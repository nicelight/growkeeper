# GrowKeeper — PRD реализации 0.2.0

**Основа:** исходный `docs/PRD.original.md`. **Статус:** реализованный private MVP с локальной верификацией; cloud/ChatGPT acceptance ещё требуется.

## Цель и границы

Вести по каждому растению/грядке Grow Case File: факты, фото, проблемы, гипотезы, эксперименты, проверки и долговременный дневник. Пользователь присылает новые сведения и не должен помнить старое состояние. ChatGPT анализирует реальные текущие и прошлые фото; backend хранит историю и проверяет инварианты.

**KISS обязательно:** один Worker, одна D1, один приватный R2; один доменный слой для MCP и web. Нет KV, Event Store, Evidence CRUD, Entity Registry, embeddings, собственного model API, hardware и multi-agent. Дополнительный слой вводится только для конкретной ошибки/пользовательской ценности.

## Существенные изменения к исходному PRD

| Изменение | Почему |
|---|---|
| UI на native JS/CSS вместо React + TS | Небольшие формы и карточки без runtime npm-зависимостей и UI-сборщика |
| Одна `inputs` table | Сохраняет и текст, и фото, пока непонятен plant; NULL plant_id у photos недостаточен для текста |
| Не привязывать по правилу «растение одно» | Новое фото может оказаться первым фото второго растения |
| Подтверждённые reference photos + порог + отсутствие конфликтов | Автоошибка не должна сама становиться новым эталоном |
| Неизвестный captured_at остаётся NULL | received_at годится только как явно обозначенная оценка порядка |
| Эксперимент начинается с PLANNED | Совет ≠ выполненное действие; ACTIVE только после сообщения пользователя |
| Journal остаётся отдельной таблицей | Выжимка результата — продуктовая память, а не UI-представление статуса |
| UNKNOWN отдельно от NO_IMPROVEMENT | Недостаток данных не доказывает неэффективность вмешательства |
| Время до результата отдельно от срока закрытия | Поздно закрытый кейс не должен увеличивать заявленное время лечения |
| NOTIFIED отдельно от DONE, delivery lease/retry | Доставка вопроса ≠ полученное наблюдение; защита от повторных запусков |
| UUID для API, SQL seq для коротких кодов | Нет отдельного registry и гонки ручного счётчика |
| Контроль версий и атомарное закрытие | Препятствует потере обновлений и дублированию итогов при retry |
| SHA-256 фото | Целостность и защита повторной загрузки, не image similarity/pHash |
| Optional native events вместо обещанной автоматически работающей Task | Реальная доставка зависит от подключённого поддерживаемого хоста и согласия пользователя |

## Пользовательский контракт

**Multi-Plant.** Каждый новый текст/фото сначала сохраняется как input. Явное имя/подтверждённый ответ на конкретную проверку или визуальная оценка дают candidate. Визуальная привязка принимается только при score ≥ threshold, наличии подтверждённого эталона того же plant и отсутствии конфликтов. Default .90, настройки .80–1.00. Это score, не доказанная вероятность. Иначе короткое уточнение; исходные данные не теряются. Автоматическая привязка всегда озвучивает имя.

**Имена.** Skill предлагает одно friendly/funny имя, оставляет возможность своего варианта. UUID постоянен при переименовании. UI даёт ручное имя и редактирование профиля.

**Фото.** JPEG/PNG/WebP до 10 MiB, приватный оригинал R2 и D1-метаданные. Один input на фото; смешанные пачки разрешаются отдельно. Кадр с несколькими неидентифицированными растениями требует уточнения, а не per-leaf tracking. Исторические кадры выбираются по plant, ракурсу, области и времени: последнее сравнимое, до фактически начатого эксперимента, около обнаружения проблемы, baseline. До трёх старых + текущий; tool возвращает реальные pixels. Различие освещения/листьев/ракурса и неизвестная дата заносятся в ограничения observation.

**Расследование.** Сначала чтение Case File/Journal; факты в observations, объяснения в hypotheses. Новое сообщение продолжает существующий Issue. Новые Issues не создаются только потому, что прошёл день. Один активный эксперимент на plant; изменение, критерий, момент начала и срок оценки обязательны. Это ограничение MVP, не научная гарантия причинности.

**Закрытие.** Согласие пользователя, свежая version и стабильный request_id. Итог RESOLVED требует ссылок на observations и даты результата; NO_IMPROVEMENT — наблюдений отсутствия улучшения; без них UNKNOWN. Одна транзакция закрывает Issue, добавляет единственный ISSUE_OUTCOME, останавливает незаконченные проверки/эксперименты и оставляет неподтверждённые активные гипотезы INCONCLUSIVE. Итог содержит реальные попытки отдельно от планов, elapsed days и time to result. Закрытый кейс не переоткрывается: повторная проблема — новый Issue со ссылкой на прежний опыт.

**Инициативность.** Followup хранит намерение. Native events после отдельной активации/подписки доставляются хосту Cron-ом, с lease, подписью и retry. 2xx → NOTIFIED; обработанный ответ → DONE. Подписка/выдача права мониторинга не включаются молча. При отсутствии поддержки хоста MVP остаётся дневником с очередью проверок, а не обещает неработающие push-сообщения.

**Чат/веб.** Короткие ответы, максимум 1–2 вопроса. В чате только реальные возвращённые backend-ссылки `H17 · название`. Один web UI: plants, case, сущности, journal, photos side-by-side, pending inputs, due checks, settings, переименование, note, upload, delete. Embedded host bridge — window.openai; standalone HTTPS-страницы не требуют встроенного bridge.

## Состояния

```text
Input:       PENDING → RESOLVED → PROCESSED
Issue:       OPEN → RESOLVED | CLOSED_NO_RESULT
Outcome:     RESOLVED | NO_IMPROVEMENT | UNKNOWN
Hypothesis:  ACTIVE | SUPPORTED | REJECTED | INCONCLUSIVE
Experiment:  PLANNED → ACTIVE → COMPLETED, либо CANCELLED
Followup:    PENDING → NOTIFIED → DONE, либо CANCELLED
Journal:     ISSUE_OUTCOME | MILESTONE | NOTE
```

## Хранение

10 предметных/пользовательских таблиц: plants, inputs, photos, observations, issues, hypotheses, experiments, followups, journal_entries, user_settings. Ещё users/auth_sessions/oauth_codes для доступа и subscriptions для optional events. Это не 14 отдельных подсистем: одна SQL-база. Точный schema — `migrations/0001_initial.sql`, ER — `docs/DIAGRAMS.md`.

JSON-массивы ссылок observation/photo/hypothesis сознательно не нормализованы в отдельные таблицы. Проверка принадлежности выполняется доменным слоем; для фото есть дополнительные SQL guards. Полный audit изменения reasoning не хранится; created/updated и версия не заменяют исторический audit.

## Приёмка

| Требование | Реализация / локальная проверка | Остаётся проверить |
|---|---|---|
| Два plant, отсутствие загрязнения историй | Domain + SQL cross-tenant/plant tests | Достоверность vision на реальных похожих растениях |
| Неопределённое фото/текст сохраняются | inputs + resolution tests | Host attachment transfer |
| Настраиваемый threshold | backend validation + widget test | Модель действительно использует фото, а не придумывает score |
| Исторические фото доступны модели | R2 adapter + actual MCP image tests | Ограничения размеров в реальном хосте |
| Persistent Issues/Hypotheses/Experiments | Domain transitions + constraints | Многодневный реальный grow pilot |
| Journal и корректные сроки | Atomic/retry/rollback/result tests | Содержательная полезность выводов для владельца |
| Entity links/Settings/Photo UI | HTTP auth tests + offline browser widget | Полный OAuth/iframe/deep links в целевом ChatGPT |
| Инициативность | Signed mock callback + Cron dispatcher tests | Реальный subscribe/delivery/unsubscribe |
| Workers/D1/R2 deployment | Конфигурация и runbook | workerd, реальный account и credentials |
